# Demonstration Coverage and Extrapolation

DataForge 2026, Pathway track.

**Source code:** https://github.com/wildcraft958/DataForge
**Live artifact:** https://web-jet-theta-42.vercel.app

## Claim

A system that learns a rule from demonstrations applies it reliably only within the complexity range those demonstrations covered. Adding a single demonstration at the harder level, changing nothing else, restores performance.

## Audience

Undergraduate CS students and early-career ML engineers who use few-shot prompting but have not thought about why it fails on hard cases.

## Prerequisites

- A modern browser (Chrome, Firefox, Safari)
- For local development: Node.js 20+, Python 3.11+, PyTorch 2.x

## Learning Objectives

After using this artifact, the learner can:

1. Explain that in-context learning success depends on the complexity range of the demonstrations, not the model's trained capability alone.
2. Inspect the gap between demonstration complexity and query complexity, and predict failure.
3. Describe how BDH-CQ stores demonstrations differently from a Transformer (recurrent synaptic state vs. growing KV cache).
4. Name the open limitation: session-scoped adaptation, not durable cross-session learning.
5. Manipulate a concept variable (coverage toggle) and observe the consequence (model output changes).
6. Compare model output with ground truth and identify where the model fails.
7. Recognize the misconception: "the model cannot do this" vs. "the demonstrations did not reach that far."

## Architecture

Three modules in a single-page React application:

1. **Live Explorer**: an ordering task (colored bars sorted by height). A complexity slider (2 to 8 bars) and a coverage toggle control which demonstrations the model sees. The model output and ground truth appear side by side with a diff overlay.
2. **BDH Substrate**: a simplified Hebbian memory visualization beside a standard KV cache. Shows how two architectures store demonstrations differently.
3. **Evidence Table**: developer-reported numbers from BDH-CQ (arXiv:2608.09888, Table 3) and a system comparison table (BDH-CQ, HRM, TRM, CoT LLMs).

## Data Labels

- **LIVE**: model inference runs in the browser via ONNX Runtime Web.
- **PRECOMPUTED**: predictions were generated offline and served as JSON. The model weights are the same.
- **SYNTHETIC**: all task data is generated by the ordering task generator. No external datasets.
- All BDH-CQ numbers are developer-reported, not our reproduction. The evidence table states this.

## Local Setup

```bash
# Install Python dependencies
pip install torch numpy pytest

# Generate training data
python3 -m generator.export --train-seeds 1500 --val-seeds 25 --web-seeds 10

# Run tests
python3 -m pytest generator/tests/ model/tests/ -v
node --test bdh-toy/tests/hebbian.test.js

# Start the frontend
cd web
npm install
npm run dev
```

## Training (requires GPU)

```bash
python3 -m model.train \
    --data data/train_tasks.json \
    --epochs 30 \
    --device cuda

# Validate the coverage cliff
python3 -m model.validate \
    --model checkpoints/model_final.pt \
    --data data/val_tasks.json

# Generate precomputed predictions for the web frontend
python3 -m model.generate_precomputed \
    --model checkpoints/model_final.pt \
    --tasks web/public/tasks.json \
    --output web/public/precomputed.json

# Export to ONNX for browser inference
python3 -m model.export_onnx \
    --model checkpoints/model_final.pt \
    --output web/public/model.onnx
```

## Week 1 Gate

At complexity 8: covered EM at least 50%, uncovered EM at most 20%, gap at least 30 percentage points.
